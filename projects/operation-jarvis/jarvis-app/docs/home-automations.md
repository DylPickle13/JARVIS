## Native behaviour

The iPhone Home shell (`JARVIS/Views/SystemView.swift`, legacy `.system` route)
places the cards after health/history and before plugs/purifier. Normal text uses
two columns; accessibility text uses one. Installed **256** uses unchanged 54-point
phone cards and places the unchanged 44-point side-by-side Watch row **below
health/history**, matching the iPhone. Watch accessibility text stacks and grows. Its existing Crown viewport and stable
outer page swipes are retained. Confirmation owns pager/Crown input and
pauses covered history; dimmed/noninteractive Watch buttons cannot send writes.

Cards display observed On/Off, Unavailable/Refreshing, or Changing/Unconfirmed.
A pending receipt is not optimistic success. Missing capabilities, stale reads,
malformed revisions, interrupted operations and unavailable connections disable
writes. An unknown result remains visible even after configuration is reread.

Enabling Barn Door Protocol requires confirmation that actions may occur
immediately or later. Disabling does **not** stop an already sounding alarm.
Automatic Voice Off prevents newly admitted announcements; speech already started
may finish. Its On state permits new qualifying events under existing source
prerequisites, not immediate speech or an override of disabled/faulted workers.

JARVISKit owns the closed commands, freshness policy, receipts and API transport.
Watch writes use either the known endpoint or the immediate-only phone relay;
there is no write fallback, background transfer, redirect, queue or retry. The
same request identity survives Watch → iPhone → backend. Old backends/phones
cannot silently promote these commands to generic device/terminal commands.

## Backend ownership

`POST /api/v1/home-automation-command` uses existing native authorization. Its
exact body is `{control, enabled, revision, confirmed, requestID}`; the request ID
must also match the native header. Only `automatic-voice` and `barn-door` with
boolean desired state are supported. No rule editing, arbitrary refs, paths,
URLs, shell text, shortcut execution, or cloud sign-in is exposed.

The optional top-level `homeAutomations` state projection is independent of health
and history classification: intentionally Off does not create a failure. Passive
`state?mode=cached` reads never trigger cloud activity. Active state reads renew a
single-flight, at-most-once-per-60-seconds cloud-read budget; cached cloud evidence
expires after 90 seconds. Reads never block the state endpoint or auto-login.

`JARVISD_SMART_ACTIONS_CLI` must explicitly select the trusted absolute Smart
Actions launcher during rollout. It is separate from `JARVISD_SECURITY_CLI`:
the installed frozen read-only sensor/status launcher is never broadened or
repurposed. Missing capability leaves Barn Door unavailable without cloud calls.
The fixed security CLI retains its device lock, fresh full-rule revision check,
private before/requested backups, one mutation and exact account readback. The
privately enrolled opaque rule ref plus automation kind/name is verified; there
is no same-name or arbitrary-first-rule fallback. Revision checks are client-side
preflight, **not server-atomic CAS**; avoid simultaneous edits in Tapo.

Slow changes return a pending receipt immediately, then update cached status.
Owner-only receipts are persisted **before** any possible change. Duplicate IDs
return the retained receipt without execution; conflicting payloads are rejected.
At capacity (512), controls fail closed without eviction; archival is an explicit
maintenance task. A daemon interruption leaves a pending reservation unconfirmed
and blocks new commands for that resource. Inspect the exact worker, cloud state
and private backups before owner-reviewed resolution; never auto-clear it based
on age, restart, or an apparent desired state. No exactly-once delivery is claimed.

## Speech integration and activation boundary

The stdlib-only shared `jarvisd_core/automatic_voice.py` owns the policy. Registered
proactive sources are `computer-arrival` and `doorbell-departure`. New unsolicited
sources must use this policy and generation checks; do not relabel automatic work
as manual to bypass it.

- Computer arrival keeps its watcher, four desk controllers and alert-relay cron
  job running. Off discards absence qualification; On begins from a fresh baseline.
  Its generation accompanies notice admission, consumption, synthesis and playback.
- Departure keeps paired sensor reads and shared dashboard snapshots running.
  Policy transitions reset only in-memory departure arming. The generation-bound
  private worker admission is rechecked immediately before doorbell playback.
- No cooldown, pending/fault latch, event proof, identity check, person-gate policy,
  volume, device address, detector commissioning or completed counter is reset.
- No suppressed event is queued, backfilled, reconstructed or retried.

Private state defaults to
`~/Library/Application Support/JARVIS/home-automations/` (directory 0700, files
0600): `voice.json`, `binding.json`, `requests.json`, and `policy.lock`.
`JARVIS_HOME_AUTOMATIONS_ROOT` is an optional trusted deployment override and must
agree in every producer and the backend. Never place state under a replaceable
release directory or restore an old receipt ledger over newer operations.

Unactivated installations retain legacy speech behaviour only when no policy
root exists and the required-policy flag is absent. After activation, **every
producer** must have `JARVIS_AUTOMATIC_VOICE_POLICY_REQUIRED=1`: missing, corrupt,
symlinked or incorrectly permissioned policy state then suppresses speech. This
compatibility boundary allows source preparation without unexpectedly muting the
currently installed services; it is not a valid activated configuration.

## 1. Mission

Stabilize and harden the existing M0–M2 implementation before adding M3 widgets and watch controls. The current code is a good working prototype, but security, service lifecycle, state latency, connection lifecycle, watch packaging, and tests must be corrected before expanding it.

The required order is:

1. **M2.1 daemon safety and correctness**
2. **M2.1 state performance and iOS reliability**
3. **M2.1 tests, packaging, deployment, and documentation**
4. **Physical iPhone regression gate**
5. **M3 watch/widget foundations**
6. **M3 UI and physical iPhone + Watch gate**

Do not jump directly to widget UI. Widget and watch extensions will multiply the current network/state lifecycle problems.

## 4. Known findings to remediate

### P0 / release blockers

1. `jarvisd` always accepts a missing token, even when strict auth is supposedly enabled.
2. `JARVIS_DASHBOARD_WRITE_TOKEN` is accepted by all endpoints rather than ingest only.
3. Wildcard CORS is enabled on unauthenticated write endpoints.
4. Stop uses `launchctl bootout`, while Start uses only `kickstart`; Start cannot reliably reverse Stop.
5. `/state` launches expensive subprocess/API work per request and has no cache or single-flight protection.
6. The state executor's documented hard timeout still waits for timed-out tasks during executor shutdown.
7. The watch app is not embedded in the iOS app.
8. `WatchBridge` implements nonexistent reachability callbacks; reachability flags will not update.

### P1 / high-priority reliability issues

1. `AppState.init` starts networking as a side effect before scene/network readiness.
2. There is no foreground reconnect, retry/backoff, or network-path handling.
3. Concurrent refresh/connect tasks can race and overwrite newer state.
4. Every tab owns an infinite poll loop; hidden tabs may continue polling.
5. A failed write is followed by `fetchState()`, which can erase the write error.
6. Plug writes use non-idempotent `plug-toggle`.
7. Missing subsystem data is rendered as valid zero/off/stopped data.
8. System and refresh errors are mostly invisible.
9. Event ingestion accepts malformed/unbounded bodies and persists an unbounded JSONL file.
10. Service-control actions are not recorded in the event feed.
11. The deploy script can select a stale `JARVIS.app` from another DerivedData directory.

### P2 / packaging and maintainability

1. No actual app icon/assets catalog exists.
2. `NSAllowsArbitraryLoads` is overly broad.
3. `UIRequiredSystemCapabilities/location` is invalid and unnecessary.
4. No Privacy Manifest exists for future distribution.
5. One Keychain write-result compiler warning remains.
6. Live tests read a hardcoded local `.env` path and can skip real regressions.
7. No daemon unit tests, mocked Swift networking tests, UI tests, or CI workflow exist.
8. README status is stale after the physical iPhone deployment.

# Part A — M2.1 daemon hardening

## 5. Workstream A1: make authentication behavior explicit and correct

**Primary file:** `jarvisd/jarvisd.py`
**Supporting files:** `jarvisd/launchd/*.plist`, `README.md`, research/implementation docs

### Required design

Introduce an explicit auth mode rather than inferring strictness merely from whether a token happens to exist in `.env`:

- `JARVISD_AUTH_MODE=trusted-network` — default for the approved frictionless setup.
- `JARVISD_AUTH_MODE=token` — require `x-jarvis-token` on protected endpoints.
- Reject unknown mode values at startup.

This avoids unexpectedly breaking the current app if `JARVIS_API_TOKEN` is present for another integration.

### Trusted-network mode

- Permit requests only from configurable trusted networks.
- Suggested env value:

```text
JARVISD_TRUSTED_CIDRS=127.0.0.0/8,::1/128,192.168.21.0/24,100.64.0.0/10
```

- Use Python's `ipaddress` module.
- Native iOS/watch requests do not send an `Origin` header. Reject browser-originated write requests by default.
- Do not emit wildcard CORS headers.

This preserves zero-tap operation while narrowing exposure. It does not make every LAN device trustworthy; document that limitation.

### Token mode

- `/health` may remain unauthenticated and disclose only health/version/uptime.
- Require `JARVIS_API_TOKEN` for `/api/v1/*` reads and writes.
- Compare secrets with `hmac.compare_digest`.
- If token mode is selected without a configured token, fail daemon startup with a clear error.
- `JARVIS_DASHBOARD_WRITE_TOKEN` must only authorize `POST /api/jarvis/events`.
- A dashboard ingest token must never authorize commands or service actions.

### Acceptance criteria

- Trusted-network mode works from localhost, the iPhone LAN source, and Tailscale.
- A source outside configured CIDRs receives 403.
- Token mode rejects a missing or wrong token with 401.
- Token mode accepts the correct API token.
- Dashboard write token works only on event ingestion.
- No response has `Access-Control-Allow-Origin: *`.
- Existing iPhone zero-tap usage still works in trusted-network mode.
- Tests cover every matrix row without printing secret values.

## 6. Workstream A2: harden HTTP input and responses

**Primary file:** `jarvisd/jarvisd.py`

Implement:

- Maximum JSON body size, suggested 64 KiB.
- Return 411/400 for missing or invalid Content-Length where appropriate.
- Return 413 for oversized bodies.
- Return 400 for malformed JSON.
- Require every API body to be a JSON object.
- Validate event payload keys and cap string/array sizes.
- Add reasonable connection/read timeouts.
- Reject unsupported methods with JSON 405 responses.
- Include a request/correlation ID in logs and write-operation events.
- Do not expose full local argv/path information in client-facing error responses.
- Keep detailed diagnostic information in local logs only.

Event ingest should reject a JSON array/string instead of allowing `dict(payload)` to throw in a request thread.

### Acceptance criteria

- Malformed JSON returns 400 without a traceback.
- JSON arrays and scalar bodies return 400.
- Oversized payload returns 413.
- Empty event bodies are rejected.
- Valid existing `jarvis.py` events remain accepted.
- Command-validation failures remain 400.
- Unknown paths remain 404.

## 7. Workstream A3: repair service lifecycle control

**Primary files:**

- `jarvisd/jarvisd.py`
- `jarvisd/services.json`

Extend each service registry entry with the LaunchAgent plist path. Support `~` expansion and validate that the resolved path is within an approved LaunchAgents directory.

Suggested schema:

```json
{
  "services": {
    "dashboard": {
      "label": "com.operation-jarvis.dashboard",
      "plist": "~/Library/LaunchAgents/com.operation-jarvis.dashboard.plist",
      "description": "Legacy dashboard (:8787) — retired in M5"
    }
  }
}
```

Implement semantics:

- **status:** `launchctl print gui/<uid>/<label>` and parse loaded/running/PID distinctly.
- **stop:** `launchctl bootout gui/<uid>/<label>`.
- **start:** `launchctl bootstrap gui/<uid> <plist>`, then `kickstart` if needed.
- **restart:** `kickstart -k` when loaded; otherwise bootstrap then kickstart.
- Verify status after every action with a short bounded poll.
- Return `loaded`, `running`, `pid`, action result, and a sanitized error.
- Do not overwrite a failed status with `{ok: true}`.
- Never permit `jarvisd` or its resurrector to be controlled through this registry.
- Record start/stop/restart outcomes in `EventStore`.

### Safe testing rule

Do not test Stop/Start against production services first. Create a disposable test LaunchAgent with a unique label and harmless sleep process. Prove Stop → Start → Restart using it, then remove it. Only perform a final dashboard/room-audio action after tests pass and with explicit user awareness.

### Acceptance criteria

- Stop transitions the test service to unloaded/stopped.
- Start restores the same stopped service.
- Restart changes PID for a running test service.
- Start works when the service is already unloaded.
- Unknown service and unknown action are rejected.
- Path traversal or an unapproved plist path is rejected.
- Every action appears in `/api/v1/events` with success/failure.

## 8. Workstream A4: make state reads cached, bounded, and fast

**Primary file:** `jarvisd/jarvisd.py`

### Required architecture

`GET /api/v1/state` must not launch fresh CLI processes. Add a thread-safe background state coordinator with:

- at most one refresh per subsystem in flight;
- cached last-good data;
- per-subsystem timestamps and stale/error metadata;
- background refresh schedules;
- command-triggered refresh of only the affected subsystem;
- fast composition of the API response from cached records.

Suggested refresh intervals:

- Pi sessions: 5 seconds
- plugs: 10 seconds
- services: 15 seconds
- purifier: 30–60 seconds to avoid VeSync rate limits
- network: 60 seconds
- weather: 600 seconds

Expose optional backward-compatible metadata:

```json
{
  "generatedAt": "...",
  "ageSeconds": 1.2,
  "stale": false,
  "refreshing": false,
  "subsystems": {
    "plugs": {
      "ok": true,
      "updatedAt": "...",
      "stale": false
    }
  }
}
```

Existing model fields must remain compatible.

### Timeout behavior

- Subprocess timeouts must terminate/clean up child processes where possible.
- Do not use a context-managed executor in a way that waits indefinitely after reporting timeout.
- Never create a new large thread pool per HTTP request.
- Concurrent `/state` requests must share the same cache and not create duplicate subprocess work.

### Startup behavior

- Start collectors in the background.
- `/health` should report daemon liveness immediately.
- If `/state` is requested before the first snapshot, return a clear temporary 503 or a documented loading response; update the Swift client to handle this as connected-but-loading.

### Acceptance criteria

- Warm `/api/v1/state` p95 response time is below 200 ms locally.
- Ten concurrent state requests do not increase `jarvis-cli` process count beyond one refresh set.
- A failed purifier refresh preserves last-good data and marks it stale/error.
- Weather and purifier are not called at app polling frequency.
- A plug command schedules an immediate plug refresh.
- Daemon remains responsive while a subsystem hangs.
- Tests use mocked collectors and deterministic clocks; they must not touch physical devices.

## 9. Workstream A5: bound event persistence

**Primary file:** `jarvisd/jarvisd.py`

- Retain a logical maximum of 500 events.
- Prevent `events.jsonl` from growing forever.
- Use safe compaction/rotation (temporary file plus atomic replace).
- Cap payload sizes and accepted fields.
- Preserve sequence monotonicity across restart/compaction.
- Keep event reads oldest-to-newest in the API; the iOS UI may display newest first.
- Add service actions to the ring.

### Acceptance criteria

- More than 500 events leave only the configured retained window after compaction/restart.
- Corrupted individual lines do not prevent loading later valid events.
- Sequence IDs do not reset or collide after restart.

# Part B — M2.1 Swift networking and lifecycle

## 10. Workstream B1: make `JarvisClient` testable and correct

**Primary files:**

- `JARVISKit/Sources/JARVISKit/JarvisClient.swift`
- `JARVISKit/Sources/JARVISKit/Models.swift`
- `JARVISKit/Tests/JARVISKitTests/*`

### Changes

- Introduce a `JarvisAPI` protocol for the operations consumed by app/watch state models.
- Keep `JarvisClient` as the production implementation.
- Avoid a shared mutable `JSONDecoder`; create one per decode or isolate decoding safely.
- Validate HTTP response type and accepted success status range explicitly.
- Parse structured server error JSON into a typed error where possible.
- Percent-encode service path components.
- Clamp client event limits.
- Add `Sendable` conformance to immutable DTOs where valid.
- Add public initializers or test fixtures needed by app previews/widgets.

### Correct discovery

Current `discover()` does not reliably return early as documented. Implement indexed candidate racing:

1. Start candidates concurrently.
2. Track each result by priority index.
3. A successful candidate may win only after every higher-priority candidate has failed.
4. Return from the task group immediately when the winner is determined.
5. Cancel remaining network tasks.
6. Return the decoded `HealthResponse` with the endpoint to avoid a duplicate health request.

Alternatively, use deliberately short sequential probes if that is simpler and measurably faster/reliable. Whichever strategy is used must have deterministic tests.

### Acceptance criteria

- A fast lower-priority endpoint does not beat an eventual successful higher-priority endpoint within its timeout.
- Once higher-priority candidates fail, a known lower-priority success returns without waiting for lower candidates.
- Cancellation terminates outstanding requests.
- Discovery handles empty and duplicate candidate lists.
- Health, state, command, events, and service errors have mocked URLProtocol tests.

## 11. Workstream B2: replace constructor side effects with a connection coordinator

**Primary files:**

- `JARVIS/AppState.swift`
- `JARVIS/JARVISApp.swift`

### Required lifecycle

- Remove `Task { await refresh() }` from `AppState.init`.
- Observe `scenePhase` in the app/root view.
- On `.active`, start or resume connection and relevant polling.
- On `.inactive`/`.background`, cancel frequent polling and in-flight nonessential refreshes.
- Keep a single owned connection task and cancel it before starting another.
- Add bounded exponential retry for transport/network-readiness failures, e.g. immediate, 1 s, 2 s, 4 s, then a slower steady retry.
- Use `NWPathMonitor` or equivalent path-change signal to retry when connectivity returns.
- Do not retry authentication/configuration failures indefinitely.
- Preserve the last good endpoint, but allow LAN/Tailscale failover.
- Mark connected after validated health; represent state loading separately.

### State model

Introduce explicit resource status rather than relying on optional data alone, for example:

```swift
enum Loadable<Value> {
    case idle
    case loading(previous: Value?)
    case loaded(Value, updatedAt: Date)
    case stale(Value, error: String, updatedAt: Date)
    case failed(String)
}
```

Equivalent separate status fields are acceptable if less invasive.

### Polling ownership

- Do not leave independent endless loops in every tab.
- Poll only while the app is active.
- Poll tab-specific resources only while that tab is selected.
- State: 10 seconds or slower; now cheap because daemon state is cached.
- Events: use `since=lastSeq` every 5 seconds and merge/dedupe.
- Services: refresh on System selection, after actions, pull-to-refresh, and optionally every 15 seconds while selected.
- Ensure intervals are measured intentionally and do not silently become request-duration + interval.

### Acceptance criteria

- Cold launch on the physical iPhone connects without pressing Connect.
- Launch during temporary network unavailability reconnects automatically when network returns.
- Foregrounding after Wi-Fi/Tailscale change rediscovers the endpoint.
- Repeated Connect taps cannot create competing state writers.
- Backgrounding stops frequent polling.
- Only the selected tab performs its tab-specific polling.

## 12. Workstream B3: make writes idempotent and user-visible

**Primary files:**

- `JARVIS/AppState.swift`
- `JARVIS/Views/HomeView.swift`
- `JARVIS/Views/SystemView.swift`

### Changes

- Replace UI use of `plug-toggle` with desired-state `plug-on` or `plug-off`.
- Pass the current/desired state into the command method.
- Track in-flight operations per resource, not with one global Boolean/string.
- Disable the affected control/card during a write.
- Ignore duplicate taps while a resource is busy.
- Do not call state refresh after a failed command.
- Do not allow a successful state refresh to clear an unrelated command error.
- Display operation errors in the relevant screen using an accessible banner/alert.
- Display brief success feedback for destructive/system actions.
- Reconcile optimistic UI state with the next snapshot, or keep the control busy until refreshed.
- Serialize purifier writes so power/mode/fan operations cannot arrive out of order.

### Acceptance criteria

- Double-tapping a plug cannot invert it twice.
- A failed plug/purifier write remains visible to the user.
- Failed service Start/Stop/Restart is visible on System.
- Controls expose busy state to VoiceOver.
- No unrelated refresh silently erases an operation failure.

## 21. Workstream E2: replace `WatchBridge` with a real relay

**Primary file:** `JARVISKit/Sources/JARVISKit/WatchBridge.swift`

Implement actual `WCSessionDelegate` callbacks from the installed SDK:

- `activationDidCompleteWith`
- `sessionReachabilityDidChange(_:)`
- iOS inactive/deactivate callbacks
- message receive/reply methods
- application-context/user-info receive paths

Design a versioned typed message envelope rather than ad-hoc dictionaries:

```text
version, type, requestID, sentAt, payload
```

Required message types:

- endpoint/config sync;
- state snapshot update;
- state request;
- plug desired-state command;
- command result/error.

Use:

- `sendMessage` for immediate reachable requests requiring a reply;
- `updateApplicationContext` for latest-state/config synchronization;
- `transferUserInfo` only for queued items that must be delivered.

Delegate callbacks must cross to the correct actor/main thread before mutating observable UI state. Do not use unsynchronized `@unchecked Sendable` state.

The watch should prefer:

1. direct daemon connection when available and appropriate;
2. iPhone relay when direct access fails;
3. last cached state with a stale timestamp when neither is reachable.

Never claim `isPhoneReachable`/`isWatchReachable` from methods not present in the SDK.

## 22. Workstream E3: shared caches and App Groups

Create app-group-backed snapshot stores:

- iOS app + iOS widget extension share one on-device cache.
- watch app + watch complication/widget extension share the watch-device cache.
- iPhone-to-watch state crosses via WatchConnectivity, then the watch writes its own app-group cache.

Requirements:

- atomic writes;
- schema version;
- generated/updated timestamps;
- bounded size;
- decode fallback if cache is corrupt;
- no token in UserDefaults/plain files;
- Keychain for credentials/config secrets;
- widget reads must be fast and must not depend on a five-second live `/state` call.

## 23. Workstream E4: iOS plug widget

Add the iOS WidgetKit target first.

- Home-screen plug grid.
- Lock-screen accessory variants appropriate to available space.
- Read cached plug state from App Group.
- Use typed App Intents for `plug-on` and `plug-off`.
- Avoid generic command strings in intents.
- After an intent, update/reload the relevant timeline.
- Clearly show stale/unavailable state.
- Respect WidgetKit background/time limits.

Do not add weather, PM2.5, Pi, or service widgets in this milestone.

## 24. Workstream E5: watch app and complication

Watch app priorities:

1. glance summary;
2. plug controls;
3. clear connection/stale state;
4. complication/widget.

Use watchOS 10+ visual language and keep interactions brief. Do not copy the entire iPhone layout.

Complication/widget:

- plug-grid/selected-plug scope only;
- interactive App Intent where supported;
- cached state first;
- relay/direct command with explicit pending/failure feedback when the app opens;
- reload timeline after state changes.

## 25. M3 physical gate

On the real iPhone 11 + Apple Watch Series 11:

- watch companion installs from the iPhone build;
- WCSession activates on both sides;
- reachability changes are observed correctly;
- endpoint/config sync reaches watch;
- state updates reach watch via application context;
- plug command reaches daemon directly or through relay and returns result;
- queued/latest state survives temporary unreachable conditions;
- iOS widget reads shared cache and controls plugs;
- watch complication reads watch cache and controls the selected plug;
- stale/offline state is honest;
- no duplicated plug toggle occurs;
- battery/network behavior is acceptable during a practical observation period.

# Part F — commit and review strategy

## 26. Keep commits reviewable

Do not create another single 5,000-line implementation commit. Suggested sequence:

1. `test: add jarvisd and JARVISKit regression harnesses`
2. `fix(jarvisd): enforce auth modes and harden request parsing`
3. `fix(jarvisd): make service stop and start reversible`
4. `perf(jarvisd): serve cached single-flight state snapshots`
5. `fix(ios): make connection and polling lifecycle-aware`
6. `fix(ios): make controls idempotent and surface stale/error states`
7. `build: make deployment deterministic and complete app packaging`
8. `docs: update M2.1 status and operating instructions`
9. `feat(watch): embed companion and implement WatchConnectivity relay`
10. `feat(widgets): add plug widgets and watch complication`

Each commit should include matching tests and documentation where applicable.

## 27. Review checkpoints

Request review after:

- daemon auth/service tests pass;
- cached state endpoint is measured;
- iOS lifecycle changes pass simulator tests;
- physical M2.1 gate passes;
- watch embeds successfully before implementing full watch UI;
- physical M3 gate passes before marking M3 complete.

## 28. Definition of done for M2.1

M2.1 is complete only when:

- auth modes behave exactly as documented;
- no wildcard CORS remains;
- malformed/unbounded request handling is fixed;
- Stop → Start works;
- warm state response p95 is under 200 ms locally;
- state collection is single-flight and rate-limit aware;
- cold physical iPhone launch auto-connects;
- foreground/network recovery works;
- hidden tabs do not poll unnecessarily;
- writes are idempotent, serialized per resource, and visibly report failure;
- subsystem failures never masquerade as zero/off/stopped;
- daemon and Swift regression tests exist and pass;
- deployment cannot select stale output;
- app icon/plist/docs are corrected;
- repository contains no secrets/runtime artifacts.

## 29. Definition of done for M3

M3 is complete only when:

- watch companion is embedded and physically installed;
- WatchConnectivity uses real SDK callbacks and works on paired hardware;
- iOS/watch caches and entitlements are configured;
- iOS plug widgets work from cache and execute desired-state App Intents;
- watch app and plug complication work on physical hardware;
- offline/stale behavior is clear;
- all simulator, unit, integration, iPhone, and Watch gates pass.

## 30. Final handoff warning

The current implementation's most important failure pattern is **comments and documentation overstating behavior**. Examples include strict auth, early discovery return, hard state timeout, and watch reachability. For every remediation:

1. test the behavior first or add a failing regression test;
2. implement the fix;
3. verify on simulator/live daemon/physical hardware as applicable;
4. only then update comments and milestone status.

Do not accept a successful build as proof that networking, watch packaging, security, or service lifecycle works.
